# Observability Dashboard

This is a standalone webapp that visualizes openclaw logs into a dashboard. This document serves as a PRD, intended to guide coding agent for concrete designs and implementations. This document is manually crafted.

## Homepage

User should see the following high-level information:

1. Top-N wechat accounts connected to this openclaw instance (ranked by last 7 days token usage). N should be configurable, default to 10 per page, max 100 per page. For each account, show last 7 days token usage.
2. Top-N agents usage. Similar to above, should support pagination and configurable N, stats over last 7 days.

User should be able to click into a wechat account or an agent, which routes them to either an "account view", or an "agent view", respectively.

## Account view

This view pivots against a single account (e.g. wechat account).

User should see the most recent N messages sent from this account. N defaults to 10, max 100 per page. Only show up to last 7 days of historical messages. The table should also display which agent(s) were involved in fulfilling the message, and the number of tokens consumed.

User should be able to click into a single message to be routed to message view.

## Agent view

This view pivots against a single agent.

User should see the most recent N messages served by this agent. Similar to above, N should be configurable the table should be paginatable. Table should also indicate which account this message belongs to.

User should be able to click into a single message to be routed to message view.

## Message view

This view pivots against a single message. There should be a top banner that shows which account and which agent(s) are associated with this user-provided message.

Next there should be a table to show the chain-of-thoughts (CoTs) (i.e. `.jsonl` logs from ` ~/.openclaw/agents/<agent_name>/sessions/<session_id>.trajectory.jsonl`) . Because each LLM API vendor (e.g. OpenAI, DeepSeek, etc.) have different CoT schema, you should dynamically figure out the table columns after you read the `.jsonl`, then allow user to select / de-select columns. You should also give user an option to preset their preferred columns to render by default.

Then there should be an eval section. Goal is to quantify the quality of this particular interaction. We should support the following eval options (they're complementary, non-competing, and user should be able to select any eval option):

1. **Perplexity**, where we calculate the perplexity of the response. For comparison purpose, we also need to compute a few baseline distributions and see where this particular user message's final generated response's perplexity fits within the wider distribution:
  a. Perplexity of all responses across all `.jsonl` logs of last 7 days.
  b. Perplexity of a subset of responses within the single account who originated this message.
  c. Perplexity of a subset of responses that are generated by any of the agents involved in this message (excluding the orchastrator agent or main agent).
  d. Perplexity of a subset of responses  that are generated by main agent or orchastrator agent.
2. **LLM Auto Rater**, where we send the question/answer pair to openclaw again for openclaw to evaluate. Do NOT trigger autorater by default. Have a button and only trigger autorater eval if user requested for it. Then render the autorater response in UI as a table. For example, use the following prompt to autorater:

```
You are evaluating an AI assistant response.

Score from 1-5:

1. Correctness
2. Relevance
3. Completeness
4. Clarity

Question:
{question}

Assistant Answer:
{answer}

Return JSON only.
```

And the autorater response might look something like this:

```
{
  "correctness": 5,
  "relevance": 4,
  "completeness": 4,
  "clarity": 5,
  "overall": 4.5
}
```
